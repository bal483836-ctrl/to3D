# 多图 + 文字融合驱动的 3D 模型生成产品方案设计

> 目标：基于**混元 3D（Hunyuan3D）**，实现「同一份 3D 模型可同时由多张图片与一段文字共同驱动生成」的产品能力。核心创新在于**双通道生成 + 多维一致性比对 + 迭代修正闭环**。

---

## 1. 产品目标与核心价值

### 1.1 一句话定义
用户上传**多视图图片**（正/左/右/背/顶/底/45°等）并输入一段**文字描述**，系统产出**一份**几何 + 纹理都符合"图 + 文"双重约束的高质量 3D 模型。

### 1.2 解决什么问题
- **单图生 3D**：背面/底部/被遮挡区域靠模型"脑补"，容易失真。
- **纯文生 3D**：几何整体形态可控，但细节（花纹、材质、比例）难以精准还原用户意图。
- **本方案**：让图片负责"看得见的细节还原"，让文字负责"全局语义与约束校正"，两者互为裁判，把两种模态的短板互相补齐。

### 1.3 与直接堆功能的区别
不是简单地"支持上传图 + 也支持打字"，而是把**文字作为一致性校验器（Constraint / Judge）**，对图生结果的几何与纹理进行**跨模态一致性比对**，发现偏差后**定向修正**。这是本产品的护城河。

## 2. 核心概念：双通道生成 + 一致性比对修正闭环

```
                     ┌──────────────────────────────────────────────┐
                     │                  用户输入                       │
                     │   多视图图片(2~8张)  +  文字描述(prompt)         │
                     └───────────────┬──────────────┬────────────────┘
                                     │              │
                 ┌───────────────────┘              └───────────────────┐
                 ▼                                                       ▼
        ┌─────────────────┐                                    ┌─────────────────┐
        │  通道A：图生3D    │  (主几何来源, primary)              │  通道B：文生3D    │  (语义参照, reference)
        │  Hunyuan3D-MV    │                                    │  Text→Image→3D   │
        │  多视图 → Mesh    │                                    │  文 → 图 → Mesh   │
        └────────┬────────┘                                    └────────┬────────┘
                 │  Model_A (mesh + texture)                            │  Model_B (mesh + texture)
                 └───────────────────────┬──────────────────────────────┘
                                         ▼
                         ┌────────────────────────────────┐
                         │      一致性比对引擎 (Judge)       │
                         │  器型 / 花纹 / 底部 / 高度 /      │
                         │  宽度 / 材质  逐维度打分          │
                         └───────────────┬────────────────┘
                                         │  差异报告 DiffReport
                          ┌──────────────┴──────────────┐
                          │  一致 (所有维度 ≥ 阈值)?       │
                          └──────┬───────────────┬───────┘
                            是 │               │ 否
                               ▼               ▼
                        ┌──────────┐    ┌───────────────────────────┐
                        │ 输出成品  │    │  修正闭环 (以图生3D为准修正) │
                        │  Model_A │    │  生成定向修正指令 →           │
                        └──────────┘    │  重跑图生3D(局部/整体) →      │
                                        │  回到比对引擎 (最多N轮)       │
                                        └───────────────────────────┘
```

**关键设计原则**：
1. **图为主、文为纲**：最终几何以图生 3D（`Model_A`）为主体，文生 3D（`Model_B`）作为"语义标尺"提供全局约束和缺失视角的补充参照。
2. **文字既是输入又是裁判**：`Model_B` 承载了文字的语义先验，用它来审视 `Model_A` 在文字未被图片覆盖的维度（如"陶瓷质感""三足鼎立""对称花纹"）上是否偏离。
3. **可解释的差异报告**：每一维度都产出量化分数 + 可视化对比，用户可介入决定是否修正。
4. **有界迭代**：修正闭环设最大轮数 N（默认 2~3），防止发散和无限成本。

## 4. 生成流水线（详细流程）

### 4.1 阶段 0 — 输入预处理
- **图片**：去背景（RMBG / SAM 分割主体）→ 归一化尺寸 → 视角识别与标注（判定哪张是正图/侧图/底图等；用户已在 UI 指定则直接采用）→ 相机位姿估计（用于多视图对齐）。
- **文字**：意图解析，抽取**结构化约束**（见 §5.1），例如从"青花瓷花瓶，细长颈，圈足，缠枝莲纹"中抽出 `{类别:花瓶, 材质:陶瓷/青花, 颈:细长, 底:圈足, 纹样:缠枝莲}`。
- 校验：图片数量 2~8（对应 UI 的 Min2/Max8），正图为必填（UI 中"上传正图"带 `*`）。

### 4.2 阶段 A — 图生 3D（主几何）
- 多张视图 → **Hunyuan3D-MV**（多视图条件）生成基础 Mesh。
- 若视图不足以覆盖 360°，用 Hunyuan3D 的视角补全能力生成缺失视角的一致性约束。
- **Hunyuan3D-Paint** 依据输入图为 Mesh 生成 PBR 纹理/贴图。
- 产出 `Model_A = {mesh_A, texture_A, 相机对齐信息}`。

### 4.3 阶段 B — 文生 3D（语义参照）
- 文字 → **文生图**（生成与文字一致的多视角参考图，可复用 Hunyuan 文生图或外接 T2I）→ 图生 3D，或直接走 Hunyuan 的文生 3D 链路。
- 产出 `Model_B = {mesh_B, texture_B}`，它是"文字理想形态"的三维化身。
- **注意**：`Model_B` 不直接作为交付物，仅用于比对与约束抽取。

### 4.4 阶段 C — 一致性比对（核心）
对 `Model_A` 与 `Model_B` 在 6 大维度逐一比对（详见 §5），输出 `DiffReport`：
```json
{
  "overall": 0.82,
  "dimensions": {
    "shape":    {"score": 0.90, "pass": true},   // 器型
    "pattern":  {"score": 0.61, "pass": false,   // 花纹
                 "detail": "A的瓶身缺少文字所述缠枝莲纹"},
    "bottom":   {"score": 0.75, "pass": true},   // 底部
    "height":   {"score": 0.95, "pass": true},   // 高度(比例)
    "width":    {"score": 0.93, "pass": true},   // 宽度(比例)
    "material": {"score": 0.58, "pass": false,   // 材质
                 "detail": "A呈现哑光陶土, 文字要求青花釉面高光"}
  },
  "actions": ["repaint_pattern", "adjust_material"]
}
```

### 4.5 阶段 D — 修正闭环（以图生 3D 为准修正）
- 依据 `DiffReport.actions` 生成**定向修正指令**：
  - 几何类偏差（器型/底部/比例）→ 局部重生成或形变约束，重跑 **图生3D**（可将 `Model_B` 的对应区域作为额外条件）。
  - 纹理/材质/花纹类偏差 → 重跑 **Hunyuan3D-Paint**，把文字约束注入贴图生成 prompt。
- 修正后回到阶段 C 复检；`overall ≥ 阈值` 或达到最大轮数 N 则结束。
- **人在环 (Human-in-the-loop)**：每轮把差异报告推给前端，用户可"全部接受修正 / 只修某几项 / 拒绝并交付当前 A / 手动补充文字"。

## 5. 一致性比对的技术实现（各维度指标与算法）

> 所有比对在**统一坐标系与统一尺度归一化**（以包围盒对齐 + ICP 配准）后进行，避免因摆放/缩放差异造成误判。

### 5.1 文字约束抽取
用 LLM 把 prompt 解析为结构化 schema，作为比对的"标准答案"来源之一：
```
category, material, sub_parts[], patterns[], proportions{h/w/d}, symmetry, color_scheme, style
```

### 5.2 六大维度比对方法

| 维度 | 中文 | 比对对象 | 方法 | 输出 |
|------|------|----------|------|------|
| shape | 器型（整体轮廓/结构） | mesh_A vs mesh_B | Chamfer Distance / IoU(体素) / 多视角轮廓 IoU；结构分件语义对齐 | 相似度 0~1 |
| pattern | 花纹（表面纹样） | texture_A vs 文字约束/texture_B | 多视角渲染图做 CLIP/DINO 特征相似度；纹样存在性用 VQA("是否有缠枝莲纹?") | 分数 + 缺失项 |
| bottom | 底部（圈足/平底/三足等） | mesh 底部区域 | 底视渲染 + 分类器判定底部形态；与文字/图底视一致性 | 类型匹配度 |
| height | 高度（纵向比例） | 归一化包围盒 | H/(max维) 比例差；与文字比例词("细长/矮胖")一致性 | 比例偏差 |
| width | 宽度（横向比例） | 归一化包围盒 | W/(max维) 比例差；左右对称性(对称面镜像误差) | 比例偏差 |
| material | 材质（PBR/质感/光泽） | texture_A(PBR贴图) | 金属度/粗糙度统计 + 渲染图材质分类；与文字材质词一致性 | 材质匹配度 |

### 5.3 打分与判定
- 每维度归一到 `[0,1]`，与**可配置阈值**比较得 `pass`。
- `overall = Σ wᵢ·scoreᵢ`（权重可按品类调整，如花瓶更看重器型与花纹）。
- 差异附**可视化证据**：并排渲染图、热力差异图、轮廓叠加图，便于用户判断。

### 5.4 "以图生3D为准修正"的落地
- 交付主体始终是 `Model_A`。文生 `Model_B` 只在**图片未覆盖的维度**上拥有话语权（例如底部没上传底图时，用 B + 文字推断；花纹在图片中模糊时，用文字约束补强）。
- 冲突仲裁规则（可配置）：
  - 该维度**有对应视角图** → 以图为准（A 优先）。
  - 该维度**无对应视角图但文字明确** → 以文字/B 为准修正 A。
  - 两者都弱 → 标记"低置信"，提示用户补图或补文字。

### 6.1 相比原截图新增/变化
1. **文字描述输入框**（必要）：与多视图上传并列，提供示例词、字数提示、结构化标签联想（自动抽取材质/器型/纹样标签供用户微调）。
2. **融合策略选择**：以图为主 / 图文均衡 / 以文校正，映射到 §5 的权重与仲裁规则。
3. **一致性阈值 & 最大修正轮数**：暴露给高级用户，控制质量与成本。
4. **生成中/生成后**：
   - 进度分阶段展示（图生3D → 文生3D → 比对 → 修正第k轮）。
   - **差异报告面板**：六维雷达图 + 逐项证据图 + "接受/拒绝/局部修正"操作。
   - 3D 预览（可旋转），可下载 `glb/obj/fbx` + 贴图。

### 6.2 交互流（时序）
```
用户: 传图(≥2, 含正图) + 写文字 + 选策略 → 点"立即生成"
系统: 建任务 → WS推进度
  → [阶段A 图生3D] 进度 25%
  → [阶段B 文生3D] 进度 50%
  → [阶段C 比对]   进度 65% + 弹出差异报告(可暂停等用户/自动继续)
  → [阶段D 修正×k] 进度 65→95%
  → 完成 100% → 预览 + 下载
```

## 7. API 设计

### 7.1 创建生成任务
```http
POST /api/v1/generation
Content-Type: application/json
```
```json
{
  "mode": "image_text_fusion",
  "images": [
    {"view": "front", "url": "...", "required": true},
    {"view": "left45", "url": "..."},
    {"view": "bottom", "url": "..."}
  ],
  "prompt": "青花瓷花瓶, 细长颈, 圈足, 缠枝莲纹, 釉面高光",
  "model_version": "hunyuan3d-v3.1",
  "face_count": "1.5m",
  "fusion": {
    "strategy": "image_primary",      // image_primary | balanced | text_correct
    "consistency_threshold": 0.8,
    "max_refine_rounds": 2,
    "dimension_weights": {            // 可选, 覆盖品类默认
      "shape": 0.3, "pattern": 0.2, "bottom": 0.1,
      "height": 0.1, "width": 0.1, "material": 0.2
    }
  },
  "human_in_loop": false             // true 则每轮比对后暂停等用户确认
}
```
响应：
```json
{ "task_id": "gen_xxx", "status": "queued", "ws": "/ws/tasks/gen_xxx" }
```

## 8. 技术栈与部署

| 层 | 选型建议 |
|----|----------|
| 前端 | React / Vue + Three.js（`<model-viewer>` 或 R3F）做 3D 预览；ECharts 画六维雷达图 |
| BFF/API | Node.js(NestJS) 或 Python(FastAPI) |
| 编排 | Temporal / Celery + 状态机（DAG：A、B 可并行，C 汇聚，D 循环回 C） |
| 推理 | 混元 3D（Hunyuan3D-2/2.1：DiT + MV + Paint）自托管在 GPU 集群；文生图可复用同栈或外接 |
| 比对 | CLIP/DINOv2（特征）、VQA/LLM（纹样与材质语义判定）、Open3D/trimesh（几何：Chamfer、IoU、ICP、包围盒）、Blender/自研渲染做多视角出图 |
| 存储 | S3/OSS（图与 mesh）、PostgreSQL（元数据/任务）、Redis（缓存/队列）、向量库(可选,存特征) |
| 观测 | 任务链路 tracing、每阶段耗时/成功率、每维度分数分布（用于调阈值/权重） |

**并行优化**：阶段 A（图生3D）与阶段 B（文生3D）无依赖，**并行执行**以缩短总时延。

## 9. 任务状态机

```
queued → preprocessing → ┬─ image3d ─┐
                         └─ text3d  ─┴→ comparing →  pass? ─是→ done
                                                       │
                                                       否
                                                       ▼
                                          (human_in_loop?) ─是→ awaiting_user →(决策)
                                                       │否
                                                       ▼
                                                   refining → comparing
                                          (round < N 且 未pass 则循环; 否则 done)
failed  (任意阶段异常且重试耗尽)
```

---

## 10. 里程碑 / 迭代计划

- **M1 MVP（打通闭环）**：多图 + 文字输入 UI；图生3D、文生3D 串起；比对先做 3 维（器型/高度/宽度，纯几何，最易量化）；单轮修正；输出 glb。
- **M2 全维度比对**：补齐花纹/底部/材质（引入 CLIP/VQA/PBR 分析）；六维雷达图 + 证据可视化；人在环交互。
- **M3 修正智能化**：定向局部重生成、冲突仲裁规则引擎、按品类自动配权重与阈值。
- **M4 体验与规模化**：并行编排、缓存复用、成本与时延优化、批量/API 开放平台。

## 11. 风险与对策

| 风险 | 说明 | 对策 |
|------|------|------|
| 双通道两次生成成本翻倍 | 图生+文生+多轮修正 GPU 成本高 | A/B 并行；文生3D 可用轻量参照(甚至只用多视角参考图而非完整mesh)；阈值高时早停 |
| 比对误判导致错误修正 | 尺度/坐标未对齐、语义判定不准 | 强制归一化+ICP；语义维度双模型投票；低置信项交人工 |
| 修正发散 | 越修越偏 | 有界轮数 N；每轮记录 overall，若不升则回滚到最优轮 |
| 文字与图片本质冲突 | 用户图文描述不一致 | 显式冲突提示 + 融合策略让用户选主导方 |
| 底/背视缺失 | 用户未传全视角 | 用文生3D + 文字补该视角约束，并在报告中标注"该区域为推断" |
